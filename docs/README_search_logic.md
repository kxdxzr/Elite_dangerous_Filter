# GUI search logic

The source additions described below ship in [v0.1.4-beta.2](releases/v0.1.4-beta.2.md).
Older “current source only / not in beta.1” notes distinguish the previous EXE.

CNB fallback remains selectable when the minimum mission-faction count is 0. In expanded searches, first combine and verify both mission and supplementary RES candidates; only return CNB when the combined filtered set has no RES/Unknown hits and both searches are complete. Supplementary RES hits suppress mission-catalogue CNB fallback. Confirmed ring-free targets can still be CNB; rings are not required for CNB.

Current source: results with known mission sources receive an additional Spansh controlling-faction lookup per unique source (at most four in flight); multiple sources are labelled individually. No source means source controller **`-`**, not the RES target's controller. Failed annotations retain the candidate, show **Unknown**, and record diagnostics. Empty display fields use **`-`** in the table and CSV, preserving explicit Unknown / No data values.

Start with `python filter_gui.py`.

The search pipeline is: copy and validate conditions → detect contradictions → resolve reference systems → fix the server query → paginate and deduplicate → check every candidate locally with AND semantics.

- A row's “is one of” selection uses OR; separate rows use AND.
- Repeated conditions on scalar fields such as economy or type are intersected. Conditions on collections such as services, ships or commodities are checked independently; a station can satisfy both Market and Shipyard requirements.
- Supported conditions are converted to Spansh's official format. Multiple collection conditions first push a union of candidates to the server, then check each requirement locally. Contains, exclusion and two-sided outside-range conditions require local verification.
- For multiple distance references, the smallest finite inside range is preferentially pushed to the server. Other references are checked precisely using coordinates. One-sided outside ranges are converted to server bounds, with strict boundaries still enforced locally.
- Multiple finite inside ranges also produce an intersection bounding volume: system queries push an x/y/z bounding box and, when tighter, search from the midpoint of two references. Every result is still checked against all original distance conditions; multi-reference queries therefore preferentially return matches near the intersection centre.
- Searches request 500 candidates per page by default to reduce network round trips. The page limit still counts requests. Engine callers can override `page_size` within 1–500.
- Searches do not mutate the supplied conditions; name corrections are returned through `corrections`. The progress bar is indeterminate during reference resolution and individual requests, then shows verified candidates versus expected candidates and the match count after each page. Completion distinguishes finished, stopped and incomplete queries.
- If a response omits a field already constrained precisely on the server, the engine can use the server's decision. If local verification requires a missing field, the record is not accepted and the missing-data diagnostic is explicit.
- Ship names (48) and module names (153) are bundled, immediately available offline, and supplemented incrementally in the background without removing existing entries. Typing provides suggestions; focus loss validates input, marking unknown names with suggestions. At search time, a typo can be corrected at similarity ≥0.85 and written back to the row.
- Result rows show matching original ship/module names when constrained, or stock-item counts otherwise. Shipyard/outfitting record age is always displayed, including Unknown.
- Freshness is integrated into ship/module rows: selling X with data no older than N days. Ships use the shipyard timestamp; modules use the outfitting timestamp. This is checked locally, and missing or stale timestamps do not qualify. Older standalone timestamp conditions remain compatible.
- Main-window and engineer-shopping module rows use one **Specification** selector (e.g. 2C, 5A, or Any), not independent class/rating selectors. The same stocked item must satisfy name, class and rating. Server nested fields AND within an item; independent conditions are separately pushed and locally rechecked. Results/CSV still split actual item names, classes and ratings into independent columns.
- Suggestions retain real class/rating pairs, never a Cartesian product. All 153 bundled module/weapon names were audited on 2026-10-17 against Spansh stock and a pinned Coriolis specification snapshot; no specification or price catalogue is downloaded at runtime. Plasma Accelerator offers 2C/3B/4A; Rail Gun offers 1D/2B. Multiple exact module names use the union of confirmed pairs. Unknown modules offer Any only, with manual specification entry still supported; missing suggestions are not proof of nonexistence. Main-window search results learn and persist actual pairs.
- Old caches with independent class/rating lists retain their metadata but never imply pairings. New caches explicitly store pairs. Old conditions/sessions with multi-value or partial specification filters retain their semantics and display a `class=... / rating=...` summary; choosing a new specification replaces those filters. Incomplete specification drafts survive sessions.

## Session saving and restoration

v0.1.1 added `language=zh/en`: display language switches immediately without converting query conditions. It saves four tools' settings, including the added PvE tool. Old sessions without a language default to Chinese, and the older `conditions` format remains readable. Pirate finding is still being tested; v0.1.0 does not contain these additions.

The main window preserves complete editor drafts, including unfinished distance and numeric conditions. Rare goods settings include source system, distance bounds, pages, filter text, Power and all-Powers selection; carrier parking and midpoint tools also preserve their settings. Changes auto-save every 1.5 seconds and on tool/main-window close. Reopening a tool restores its parameters. Session files use a temporary file followed by atomic replacement; failed close-time saves report an error and keep the window open.

The v0.1.2 colonisation tool additionally preserves optional inputs, planet/ring group modes and editable condition-group drafts.

## Result completeness

### Main-window system detail filters (v0.1.2)

In **systems** mode, ordinary field rows now also support local numeric counts: `station_count` (all stations, including carriers), `carrier_count`, `minor_faction_count`, `federation_faction_count`, `empire_faction_count`, `alliance_faction_count`, `potential_issuer_count`, `federation_issuer_count` and `empire_issuer_count`. The first faction-count family includes Anarchy; issuer estimates exclude Anarchy and do not guarantee live missions. Names are deduplicated case-insensitively. Missing/conflicting required evidence remains unknown, never zero. Missing station lists are verified against the station endpoint.

Use **+ Planet / nearest-populated conditions → Edit detailed conditions…** to add reusable planet and independent ring groups. Conditions within a group match the same planet/ring; groups use all/any existence semantics. These groups AND with ordinary rows and other detailed rows. The original `bodies`/`stations` field rows still match names; they are not the new nested editor.

The same editor optionally verifies distance to the nearest system whose population is strictly greater than an editable threshold (default 1). Both distance bounds blank disables it; otherwise inclusive one-/two-sided bounds apply after finding the nearest qualifying system. Ordinary reference-distance rows independently set the regional search area. The existing raw `distance_to_nearest_populated_system` field remains separate and does not imply this verified population definition.

These main-window filters do **not** impose colonisation eligibility: populated systems, systems with stations and permit systems can match unless ordinary rows explicitly exclude them. Local derived names and group specifications are never sent as Spansh server fields. Cheap ordinary/distance conditions run first, then counts, then bounded full-body requests and nearest-neighbour verification. Unknown evidence is reported, and cancellation never accepts unverified candidates. Diagnostics also prepare the required local evidence.

Raw editor drafts, condition-file loading and session restoration preserve the additional rows and nested groups. Switching to station queries retains detailed drafts but prevents running system-only conditions. Results retain detailed evidence internally. CSV exports the completed search's requested fields, computed counts, matched planet/ring groups and verified neighbour names/populations/distances as readable columns instead of a full raw JSON dump. Missing ordinary values are labelled unknown, never replaced with the requested filter value.

### PvE rules (testing)

- Candidate source/unique-target pairs come from EDTools PvE. Explicit `haz/high/reg/low/res` records remain confirmed sites unless contradicted by a confirmed zero ring count. By the agreed convention, rings imply **RES (inferred from rings)**, never Low. Pairs without site/ring information are **Unknown**, not proof of no RES. Confirmed ring-free targets have no RES even if stale site records list one; CNB is judged independently and may still qualify for fallback. This correction is in current source, not the published v0.1.4-beta.1 EXE.
- Distance is from mission source to reference. Radii ≤250 ly use the explicit PHP page, accept thousands-separated row counts such as `8,420`, verify actual row counts and reject truncation or insufficient coverage. Radius `0` or >250 ly uses public `pve.json` and `res.json` with coordinate distances; `0` disables distance filtering and is not limited by the page's 250 ly ceiling. Complete data means the supplied EDTools catalogue, not the actual whole galaxy.
- Source faction presence, source/target controlling minor factions, total/Federation/Empire minima and controlling Power requirements all use AND. Counts accept `0–8`; Federation and Empire are independent minima.
- Source pad S/M/L is a ship-size requirement, with larger pads compatible. Source-station maximum arrival Ls and target-ring maximum arrival Ls also use AND. Blank disables these constraints; distance 0 is a real, inclusive bound. Source pad and distance must match the same station with Missions service. Planetary stations are included; carriers, Stronghold Carriers and colonisation ships are excluded. Colonisation-ship name/real-name checks are reused to reject ships misclassified as Planetary Outposts. Results record the nearest matching station, largest known pad and arrival distance.
- Ring distance comes from full `/bodies/search` records' `rings` and `distance_to_arrival`; system summaries cannot prove absence of rings. It is arrival Ls to the nearest known ringed body, not ring radius or a specific RES position. After other filters, targets are batched in groups of at most eight systems with at most four in-flight requests, complete pagination, deduplication/repeated-page protection and a five-minute cache. Unknown distances do not meet an explicit maximum and generate incomplete diagnostics. Cancellation does not return candidates with unverified ring conditions or trigger CNB fallback.
- Current source also checks otherwise **Unknown** EDTools targets against Spansh body records when no ring-distance maximum is set. Found rings promote the target to inferred RES, never Low. If body records are returned, pagination completes and no rings or malformed ring records are found, exclude the target; this means no rings in the available Spansh data, not proof of complete in-game exploration. Empty coverage, errors and uncertain ring data preserve Unknown and block CNB fallback. Rings with unknown arrival distance can qualify only when there is no distance maximum. Successful ring evidence is recorded in the result/CSV. This is not yet in the published v0.1.4-beta.1 EXE.
- **Expanded RES search (current source only):** minimum mission factions **0** retains mission results and adds Spansh RES-system candidates; **1–8** uses the original mission search only. No separate mode selector. Saved minima, including older 0 values, determine the behaviour. At 0, source filters are disabled but preserved. Supplementary systems use target controlling faction / Power and target radius; existing mission rows retain source-radius/distance semantics. Spansh queries read complete pages (up to 100 × 500), ignore capped counts, and fail on repeated pages or the page limit. Use bounded body batches and cache; zero-ring body evidence excludes targets, including stale mission rows. Unknown ring coverage cannot create an inferred hit, while positive ring evidence does not require known arrival Ls unless a distance maximum is set. Low / Regular / High / Haz and confirmed-only require explicit site records. Retain existing task-pair rows and their counts; upgrade their site evidence when verified, then append new targets only. Reuse Mission source for all known sources, or No data if unlisted, and never invent/aggregate unrelated faction counts. Known sources rank first, then explicit RES, preferred Low and distance. EDTools failure does not discard Spansh candidates, but marks the run incomplete. Imported HTML only scopes the mission portion. Not in v0.1.4-beta.1 EXE.
- Source-station/ring conditions and result columns are included in both UI languages, CSV and restored sessions. The separate source-copy action was added; double-click continues to copy the target.
- Spansh's controlling-faction server filter is case-sensitive. On an initial empty result, official names are looked up and only a case-insensitive full-name match can be retried with official casing. Keyword/fuzzy candidates are not substituted and user input is not rewritten. Name-service failures are errors, not empty control lists.
- Nonzero faction minima use deduplicated Spansh non-Anarchy minor factions as potential-issuer estimates, not live mission counts. Power filtering strictly uses `controlling_power`, applies to source, target or both, and does not use associated `power` lists.
- All conditions are applied before selecting explicit/inferred RES; unknown-site candidates are labelled separately. Low affects ordering, not eligibility, and Unknown sorts last. CNB fallback occurs only after complete checking finds no qualifying explicit/inferred RES and no unknown-site candidates. Missing required filter data, request errors and cancellation disable fallback. Unknown sites do not necessarily mean interrupted processing: the catalogue can be fully checked while in-game site availability remains unknown.
- Controlling-faction filters first paginate Spansh control lists, intersect them exactly with EDTools pairs and reuse faction data from batch responses. Potentially capped `count` is not used to decide completion. Repeated pages, missing fields and exhausted limits are errors, not complete coverage. Controlled systems without EDTools pairs appear only in coverage diagnostics; targets are not invented.
- Controlling Power similarly prefilters through `controlling_power`, not associated `power`. Pagination uses gzip when available, at most four in-flight requests and 500 rows per page, processed in page order. Short/empty pages determine coverage; totals are not trusted. Up to three boundary-exceeding requests can already be in flight and their results are ignored. Cancellation stops new requests. Only complete, valid lists are cached for five minutes; forced refresh bypasses them. Source/target/both share lists and faction details. Target Power combined with source-count constraints may require detail requests for remaining sources outside the Power list, rather than querying the entire mission catalogue individually.
- EDTools pages/JSON cache for one hour; Spansh control lists/details cache for five minutes in data-directory `pve_cache_*.json` files, with at most 256 memory entries. Only successful data is cached. Expired/forced-refresh failures raise errors without silently using old data. **Refresh data and search** exits imported mode and refreshes the online data required by the query.
- System details use at most four in-flight requests, submitted as needed. Cancellation stops submission but executing HTTP requests must finish or time out. Pairs are deduplicated, details reused and unqueried controller/update fields left blank.
- Progress is throttled to 150 ms across resolution, download, control prefilter, details and verification stages. Diagnostics include stage timings, cache acquisition times and coverage/rejection reasons. PvE GUI rows render in batches of 200 with event-loop yields, without truncating search or export results.
- EDTools uses explicit `/pve.php`, avoiding Apache MultiViews ambiguity between extensionless `/pve` and `pve.json`, which caused HTTP 406. Full online searches were verified. Errors retain the requested URL and support opening the page/saving HTML for import. Imported site/radius-only searches can be offline; extra faction/Power requirements still contact Spansh.
- Three minor-faction fields use Spansh `minor_factions?q=` to select full names. Keywords and spelling similarity rank suggestions only; exact-match semantics and input remain unchanged. Suggestion failures and empty suggestions have separate messages and do not prove nonexistence. Stale asynchronous responses cannot overwrite current suggestions.
- Suggestions track actual text changes, including paste/IME, preserve real punctuation, select mouse candidates on press, cancel invalid timers and clean up traces/widget references on close.

Measured on 2026-10-14: `Sol / radius 0 / minimum 3 factions / source controller Skyline Monopoly`. The online catalogue had 28,121 pairs; Spansh returned 507 controlled systems, with 138 catalogue matches and 369 without pairs. Under the old rules, all 138 targets lacked explicit RES/CNB records, yielding zero results. The revised rules checked 138 sources, rejected one for insufficient count and returned 78 inferred RES + 59 Unknown = 137, with zero explicit RES. Forced refresh took about 13.49 s; an immediate cached repeat took 0.13 s, with identical results and six progress callbacks each. These backend measurements exclude GUI rendering; upstream data changes.

Same-day Power measurement: `Sol / radius 0 / minimum 3 factions / Yuri Grom / source`. Spansh returned 1,634 controlled systems, intersecting 128 sources; four failed counts, leaving 124 (8 explicit RES, 54 inferred, 62 Unknown), without individual detail requests. Initial serial/uncompressed batches took about 79.39 s for refresh; gzip with at most four concurrent pages took 15.37 s, followed by a 0.19 s cached repeat with identical result sets. Both-end filtering returned 47 (3 explicit, 27 inferred, 17 Unknown), reusing cache in about 0.26 s, with both Powers verified per row. These local measurements do not guarantee timings for other Powers or networks.

### General searches

- **Requested result count reached:** the first matches are returned, not all matches.
- **Candidate pages exhausted:** the supplied candidates have been traversed; missing-field diagnostics can still indicate unconfirmed candidates.
- **Page limit reached:** incomplete search; zero matches does not prove the database has none.
- **Cancelled:** only matches confirmed before cancellation are returned. Executing network requests finish or time out before processing stops.
- **Repeated server candidates:** stop and report incomplete coverage rather than loop through duplicate pages.

Spansh counts can be capped at 10,000 and are not exact whole-database totals. More pages enlarge verification coverage; queries with local conditions need not finish in one request.

## Carrier parking finder (v0.1.2)

Open **Extra tools → Carrier parking**, enter a reference and radius (default 30 ly, maximum 50 ly), and find parking candidates using catalogued carrier counts, ordered by distance. Pages contain 500 systems, with 20 pages by default. Exhausted pages and reached limits are distinguished. Cancellation, double-click system copying and CSV export are available.

- Carrier counts include station types containing `Carrier`, case-insensitively (including Fleet Carrier and Drake-Class Carrier). Station totals remain a separate reference column and never determine carrier counts or parking availability.
- Optional minimum/maximum carrier counts are non-negative integers and inclusive. Blank means unrestricted; maximum `0` selects confirmed zero-carrier records. Unknown counts cannot satisfy a count bound.
- Missing/malformed station lists or missing/blank station types produce Unknown, not zero. An explicit empty station list counts as zero.
- By default, count bounds are blank and only explicitly permit-free systems are shown. Settings, including unfinished count bounds, are saved with the tool session.
- These are catalogued counts, not live carrier positions or parking predictions. Spansh can lag movements. System record age uses `updated_at` and does not guarantee every carrier position is equally recent. The v0.1.1 EXE and its screenshots retain the old parking-estimate tool.

## Rare goods target finder

Open **Extra tools → Rare goods target finder**. The default reference is Ngurii; sources come only from the supplied rare-goods list (142 entries, 138 distinct systems). Filter choices by system, goods or source station. Selection shows every associated good/station, with each source system listed once; entries originally marked Supply=0 remain available. Sources are bundled in `rare_goods.py`; snapshot prices, profits, stock and distances are not used.

The search finds target stations 200–220 ly from the chosen goods source (inclusive, editable), not goods-selling source stations. Targets need large pads and arrival distance ≤100 Ls; planetary stations, carriers and colonisation ships are excluded. Colonisation-ship checks use name, real name and type, including `$EXT_PANEL_ColonisationShip`, to catch nonplanetary Planetary Outpost misclassification. Exclusion occurs before fallback decisions and top-five selection. The updated v0.1.2 EXE removes the redundant range column from the detail table and CSV, leaving six columns: associated Power, system, station, ly distance, arrival Ls and station record age. Search fallback rules are unchanged.

- Select associated `Power`, not `Controlled`. Arissa Lavigny-Duval maps to Spansh's `A. Lavigny-Duval`.
- All-Powers mode scans all 12 bundled Powers and groups results by association. A station can belong to multiple Powers; each group deduplicates. Summaries show station/system counts, arrival limits and completion. Selecting a summary filters details. Copy system, export all groups (including empty groups), search notes and cancellation are supported.
- **Independent fallback per Power:** only a fully paginated 100 Ls search with no matches allows that Power to search ≤1000 Ls. Powers with standard-range matches are not expanded. Only two complete empty rounds mean no results; limits, missing fields, cancellation and failures do not.
- Each round uses 500 stations per page and its own page limit. All-Powers searches batch the union of Powers and group locally instead of repeating queries per Power.
- Each Power deduplicates by system, retaining its nearest eligible station as a reference, then sorts by source-to-target ly and arrival Ls. At most five systems are displayed per Power. Unrounded distances determine ordering. Searching and fallback finish before deduplication and top-five selection. Summaries count all confirmed systems, not stations; details and CSV contain one row per displayed system per group.
- **State limitation:** Spansh `Unoccupied` currently approximates Inara's Unoccupied / Expansion / Contested union. This has not been verified against actual samples; equivalence is not guaranteed and Expansion/Contested cannot be selected separately. The UI includes this explanation; CSV does not add a note column.

## Colonisation candidate finder (v0.1.2)

This tool is included in the v0.1.2 EXE. Construction-slot count filtering is not included; the pirate massacre finder remains in testing.

The updated v0.1.2 EXE removes the colonisation maximum-page control and ignores legacy saved page limits. Candidate and nearest-populated lookups page automatically until a result is established, supplied candidates are exhausted, the requested result count is reached or cancellation/error interrupts the query. Repeated pages remain incomplete, not proof of exhaustion. Without regional bounds, restrictive searches may be lengthy. Other tools retain their page controls.

- Three requirements are mandatory: `population == 0`, no stations (including carriers), and `needs_permit == false`. Unknown population/permit data never qualifies. If the system response omits `stations`, the station endpoint is fully queried to verify absence; omission alone is not proof of zero stations.
- Two independent optional ly filters are provided: **regional reference + maximum radius**, and **minimum/maximum distance to the nearest system with population >1**. Each section can be left blank; enabling both combines them with AND. A regional radius needs a reference; the nearest-populated section does not. Blank bounds are unrestricted, 0 is an actual bound, and distance boundaries are inclusive. Minimum-only and maximum-only nearest-distance filters are supported.
- The nearest populated system is found first, then its distance is checked against the bounds. This is not an existence test within an annulus: with a 5–10 ly requirement, a target whose nearest populated system is 2 ly away fails even if another is 8 ly away. The lookup sorts around the candidate's coordinates, verifies population and coordinate distances, and checks returned ordering rather than using `nearest_populated_distance` without validating its population definition. Uncertain records cannot establish a nearest match. Results show the nearest populated system's name, distance and maximum fixed-station pad, not its population; older maximum-only saved settings remain compatible.
- System value is independently optional. Blank means unrestricted; values must be strictly greater than a filled threshold. The selected field is `estimated_mapping_value`, `estimated_scan_value` or `landmark_value`.
- Add planet groups with any number of conditions. Every condition within one group must match the same planet. Between groups, AND means every group has a match; OR means at least one has a match. One planet can satisfy multiple groups. No groups means unrestricted.
- Ring conditions within a planet group require that planet's own ring; multiple ring conditions must match the same ring. Independent ring groups can match any body's ring without requiring it to belong to a planet matched elsewhere. Independent groups also support AND/OR and are ANDed with the planet section and other enabled constraints.
- Available properties include subtype, landability, terraforming, gravity, arrival Ls, temperature, pressure, atmosphere, volcanism, size/mass, rotation/orbit fields, reserves, surface materials, signal types/counts and body scan/mapping values. Ring fields include type, inner/outer radius and source-unit mass. Use `in` with `|`-separated choices, `between` with `min|max`, and `true`/`false` for booleans.
- Moon status uses the immediate planetary parent. Having moons uses recorded immediate planetary children. Binary membership is **inferred**, requiring exactly two recorded planetary siblings at a shared immediate virtual `Null` barycentre and matching nonzero orbital periods, with no missing planetary parent information. Shared stars, tidal locking and shared barycentres alone are insufficient; complex/missing structures are Unknown. Results show related names. Planet-group AND does not assert that matches in separate groups orbit each other.
- Full body records are loaded in batches of eight systems with at most four in-flight body requests. Successful body/station verification data caches for five minutes; refresh bypasses those caches. Missing required values cannot satisfy either positive or negative conditions. No body records means unknown coverage when body/ring requirements are enabled.
- Result limits, repeated pages and cancellation report incomplete coverage. Confirmed partial matches can be returned on cancellation. Results show matching planets/rings by group, inferred relationships, the nearest populated neighbour and distance when requested, and the selected system value. Copying, CSV, bilingual display and saved drafts are supported.
- Updated v0.1.2: the top three recorded planets by `estimated_scan_value` are shown with name, subtype and Cr, including in CSV. Stars are excluded; ties sort by name. Missing/invalid/negative values are not treated as zero or replaced by mapping values. Missing prices or a body-count mismatch mark coverage incomplete, so this is a known-value ranking rather than a guaranteed system-wide top three. Existing system body summaries or already-fetched full bodies are reused without additional price-only requests.
- The nearest populated system (population >1) is labelled as such; its population is used internally, not shown as a table/CSV column. A separate copy button copies its name. The maximum fixed-station pad (S/M/L) is taken from that same nearest-system record, excluding carriers and colonisation ships; unknown data is not inferred. This display does not change the chosen neighbour or add a separate request.
- General search and midpoint results exclude the anomalous Spansh `Test` system (ID64 `7780433924818`) and general station searches exclude its stations. Other system names merely containing `Test` are unaffected; colonisation eligibility also excludes this record.

Regression checks: `python -m unittest discover -v`.
